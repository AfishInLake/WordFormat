## 0. 结论摘要

1. **真正阻塞跨文体泛化的不是模型，也不是规则本身，而是论文域规则已经渗进了解析层内部。**
   `base.py` 名义上是核心，实际 85% 是论文域逻辑，且在 `parse()` 中被无条件执行。

2. **标签集在代码中已存在四个副本**，其中 `tree.py` 的副本完全硬编码、不读注册表，新增类别时会静默降级而不报错（§2.3）。这是新增任何领域之前必须先消除的正确性隐患。
   `tree.py` 副本已于缝 B 落地时收敛为注册表派生（2026-09-29），UI 侧副本（§2.3 副本 4）仍待缝 D。

3. **推荐边界：核心保留领域无关的文档处理能力，领域包内聚"标签集 + 阈值 + 规则 + 权重"四元组。**
   四者必须同版本交付，不可拆成彼此独立的加载单元（§3.2）。

4. **优先级：先拆后处理链（缝 A，低风险、解锁公文），再拆注册表（缝 B，正确性前提）。**

5. **分发形态需与接口一并设计**：模型占包体约 83%，领域包应可单独安装。注意 `pip` extras **无法**减小 wheel 体积，必须用独立发行版（§3.5.1）。

6. **公文首版建议只含规则、不绑模型**，即可完全绕开体积问题，也符合公文"强规则域"的特性（§3.5.3）。

7. **落地前应先做真实验证**（§7）——本文档中"论文规则在公文上产生负收益"的判断来自静态推演，未经样本验证。

## 1. 背景与目标

`WordFormat` 当前面向学术论文：用 ONNX BERT 对段落做分类（标题 / 摘要 / 关键词 / 参考文献 / 正文…），再按 YAML 配置校验并修正格式。

目标是把能力扩展到**公文 / 材料**方向。这需要的不是"换一个模型"，而是让**领域相关的全部知识**（类别体系、判定规则、阈值、模型权重）成为一个可替换的整体，同时保持领域无关的文档处理能力稳定复用。

## 2. 现状盘点（证据）

### 2.1 `base.py` 名义是核心，实际 85% 是论文域规则

> 注：本节为落地前的现状盘点。缝 A 已于 2026-09-29 落地——`base.py` 现为 92 行纯编排（加载 + 批量推理 + 领域分派），下文行号与函数名均为历史形态，迁移目标是 `domains/thesis/postprocess.py`。

`src/wordformat/base.py` 共 628 行：

| 区段 | 行号 | 性质 |
|---|---|---|
| 模块级常量 | 20–148 | **论文域** |
| `class DocxBase` / `parse()` | 151–244 | 通用（含少量域逻辑） |
| 后处理函数 ×13 | 245–628 | **论文域 ~10 / 近似可用 1 / 项目通用 1** |

`parse()` 本身只做三件事：遍历段落、批量 ONNX 推理、按阈值过滤 —— 这部分是通用的。

模块级常量同样如此（`base.py:20-148`）：`SECTION_START`、`SECTION_CONTENT`、`BODY_HEADINGS`、`REF_ITEM_PATTERN`、`ABSTRACT_CONTENT_TO_TITLE`、`ABSTRACT_TITLE_PREV_CATS`、`COVER_MARKER_PATTERN`、`ABSTRACT_CONTENT_GATE_*`、`APPENDIX_NEUTRALIZE`、`TOC_PATTERN`、`ABSTRACT_TITLE_MAXLEN` —— 全部为论文域。

### 2.2 这条链对非论文文体的作用是负的

领域无关的"后处理"应当是可替换的**领域规则**，而非普遍适用的清洗步骤。当前这条链在公文上会产生实际损害：

- **`_neutralize_appendix`（`base.py:375`）**：一旦模型输出 `heading_fulu`，从该点起到下一个高置信 `heading_level_1` 之间的摘要/关键词/致谢类标签会被强制抹成 `body_text`。
  `structure/settings.py:37` 的注释明确写着 `heading_fulu` 是"模型真实标签"（附录段落必然触发）。
  **而公文有"附件"** —— 论文模型把附件判成附录是高概率事件，触发后附件之后的整段内容被错误中性化。
- **`_apply_section_state`（`base.py:401`）**：由论文标题驱动的状态机，把章节内 `body_text` 改写为 `abstract_content` / `references_content` 等。公文正文中只要出现"参考文献"字样即误触发。
- **`_mark_cover_as_other`（`base.py:440`）**：以 `摘要|Abstract` 作为封面边界，公文无摘要 → `abstract_start is None` → 直接 early return。属于无害空转，但印证了整条链"论文专用"的性质。

#### `_fix_heading_levels` 是唯一的反例，也是最值得注意的一点

`base.py:355` 用层次序数正则反推标题层级 —— **这恰恰是公文最强的结构信号**（`一、`/`（一）`/`1.`/`（1）`）。

但现有正则集是论文的：

| 常量 | 行号 | 现状 | 公文需要 |
|---|---|---|---|
| `_HEADING_CHAPTER_RE` | 111 | `第X章` | 不适用 |
| `_HEADING_NUM_RE` | 113 | `1.` / `1.1` / `1.1.1` | 仅对应第 3 层 |
| `_HEADING_CN_NUM_RE` | 115 | `一、` 等 | 对应第 1 层 ✓ |
| `HEADING_LEVEL_CATS` | 109 | 仅 3 级 | **需 4 级** |

**结论：公文需要的是"改写这条规则"，而不是"启用 / 禁用这条规则"。** 因此领域规则接口必须是**整体替换**语义，而非布尔开关 —— 这一点直接决定了 §3.3 的接口形态。

### 2.3 标签集在代码中已有四个副本

| # | 位置 | 性质 | 新增公文类别时 |
|---|---|---|---|
| 1 | `structure/registry.py:12-13` 全局 dict，由 `@register` 写入 → `settings.CATEGORY_TO_CLASS` / `settings.LEVEL_MAP` | 权威来源 | 正常 |
| 2 | `settings.py:31-38` 的 `setdefault` 块（`other` / `document_title` / `footer` / `heading_mulu` / `heading_fulu`） | 手工补丁 | 需手工同步 |
| 3 | `tree.py:195-224` 中 `_build_simple_tree()` 内的 `HEADING_CATEGORIES` + `LEVEL_MAP` | **完全硬编码、不读注册表** | **静默分歧** |
| 4 | `WordFormatUI/src/composables/useTagHelpers.js:41-65` 的 `CONF_THRESHOLDS`（`base.py:19` 注释所指） | 跨仓库双写 | **已实测漂移，见 §3.6.1** |

第 3 处是演示用树构建器（docstring 自述"不依赖 config，仅用于展示"），不影响主管线正确性，但它在 `tree.py:233` 以 `LEVEL_MAP.get(category, 999)` 取值，**任何新增类别会静默降级到 999 而不报错**。

> 标签副本的存在是架构信号：只要领域知识分散在多处硬编码中，"新增一个领域"就永远伴随着静默错误。

### 2.4 注册表是 import 时写入的全局可变对象

`settings.py:26-40`：

```python
from wordformat.structure.registry import _level_registry, _registry
CATEGORY_TO_CLASS = _registry      # 不是副本，是同一个对象
LEVEL_MAP = _level_registry
```

即：**`CATEGORY_TO_CLASS` 是一个全局可变对象，其内容取决于 `settings.py` 恰好 import 了什么。** `settings.py:6-24` 那个硬编码 import 列表正是为此存在，且同文件注释已警告：漏掉一个 import 会导致"节点-段落错位"。

两个直接后果：

1. 哪些规则生效**无法在运行时确定**，只能靠维护 import 列表；
2. 两套领域规则**无法共存** —— 它们会向同一个全局 dict 注册同名类别并互相覆盖。

### 2.5 模型层已经基本解耦

`agent/onnx_infer.py`（252 行）只暴露 `onnx_batch_infer` / `onnx_single_infer`，`DocxBase`（`base.py:11`）也只 import 这两个，耦合面很窄。

真正跟随标签集的是 **`base.py:20` 的 `CONF_THRESHOLDS`**（按类别的置信度阈值字典），它是论文域的，必须随标签集一同迁移。

### 2.6 解析层存在与模型无关的召回缺口

`base.py:170`：

```python
all_paras = list(self.document.paragraphs)
```

只取正文段落，因此读不到：

- **页眉 / 页脚**（公文页码、密级等）；
- **文本框**（大量公文模板把正文放在文本框里）；
- **表格内段落**（公文的多级标题常出现在表格中；`document.paragraphs` 不含表格内容）。

这是**召回缺口而非精度问题**，任何模型或数据集都解决不了。且它是领域无关的核心能力，**不属于领域包范围**（见 §4.3）。

### 2.7 分发形态：模型占包体约 83%，且资源锚点硬编码

`src/wordformat/` 合计 11 MB，其中模型占绝大部分：

| 文件 | 体积 |
|---|---|
| `data/model/thesis_paragraph_classifier_int8.onnx` | 8.99 MB |
| `data/model/tokenizer.json` | 0.49 MB |
| `src/wordformat/` 合计 | 11 MB |

即**约 83% 的包体是模型**。多领域共存意味着包体近似线性增长。

三处相关事实：

**1. 打包使用显式白名单**（`pyproject.toml:129-142`），注释记录了成因：

```

```

对应 1.6.1 那次 69MB→6MB 的修复。多领域后需继续保持白名单形态。

**2. 资源锚点硬编码**（`agent/onnx_infer.py:33-36`）：

```python
def _get_model_dir():

    return files("wordformat.data.model")
```

锚定 `wordformat` 包内的固定路径。**独立发行版中的模型无法被加载** —— 这是"单独安装"必须打通的必要条件。

**3. 独立二进制打包另行内嵌模型**（`scripts/build.sh:49-52`）：

```
--add-data "src/wordformat/data:wordformat/data"
--hidden-import=wordformat.data
```

PyInstaller 路径需随分发形态同步调整。

此外，**按需下载路线已被主动退役**。`scripts/download_model.py` 的 docstring 记录了原因：

```

不再需要从 GitHub Release 下载。此脚本仅保留版本检查逻辑：
```

即项目**从下载迁移到了随包分发**，并保留了守卫逻辑防止回退。`settings.py:37-38` 的 `WORDFORMAT_MODEL` / `WORDFORMAT_MODEL_URL` 已无消费方。

## 3. 推荐架构：领域包

### 3.1 核心保留职责（领域无关）

以下能力必须留在核心，它们不随文体变化：

1. docx 解析与元素抽取（含 §2.6 需扩展的页眉页脚 / 文本框 / 表格）
2. 段落 ↔ 树节点按位置对齐（`pipeline/stages.py`）
3. 树的构建与后处理（`structure/tree_builder.py`）
4. 格式 diff / apply（`style/diff.py`）
5. CLI / FastAPI 接口层

### 3.2 领域包的内聚单元

一个领域包**整体交付**以下四项，缺一不可：

> **标签集 · 置信度阈值 · 后处理规则 · 模型权重 —— 必须同版本。**

原因：这四者构成一个不可分割的语义单元。一旦它们可以独立加载，就会出现**"A 领域的规则 + B 领域的权重"这种可加载且无报错的组合**，其表现为静默的质量塌方，而非显式失败。让它们内聚是消除这一类失效模式的前提。

### 3.3 接口草案

```python
class DomainPack(Protocol):
    name: str
    categories: dict[str, type[FormatNode]]   # 取代全局 _registry
    levels: dict[str, int]                    # 取代全局 _level_registry
    thresholds: dict[str, float]              # 取代 CONF_THRESHOLDS
    model_path: str                           # 与以上四项同版本
    extra_imports: list[str]                  # 触发 @register 的模块清单

    def postprocess(self, result: list[dict]) -> list[dict]: ...
    def export_defaults(self) -> dict: ...    # 取代 registry.export_defaults()
```

要点：

- `postprocess` 是**整体替换**语义（见 §2.2 结论），不是规则开关列表；
- `export_defaults()` 取代 `registry.py:47` 的全局遍历，使 `wordf config -o` 能按领域导出模板，并可作为 UI 侧 `useTagHelpers.js`（§2.3 副本 4）的统一供给源，消除跨仓库双写。

首批两个包：

| 包 | 内容 |
|---|---|
| `papers` | 现有逻辑原样搬迁，行为零变化（回归基线） |
| `govdoc` | 新增。公文是**强规则域**（GB/T 9704-2012），规则层权重高于模型层 |

选择方式：配置 YAML 增加 `domain:` 字段，CLI 增加 `--domain` 覆盖。

### 3.4 领域包的发现与加载

当前阶段用**内部两个包**把接口跑通即可，经配置 `domain:` 字段与 CLI `--domain` 显式选择。`importlib.metadata.entry_points` 的外部插件发现机制留作演进方向，待出现第三方接入需求时再引入。

但接口需**为独立发行版留出位置**（§3.5）：领域包若作为单独发行版安装，模型锚点必须可解析到另一个包，而非 `wordformat` 内的固定路径。

### 3.5 分发形态与体积

#### 3.5.1 约束：extras 不减小 wheel 体积

`pip install wordformat[papers]` 中的 extras **只控制依赖解析，不改变 wheel 自身内容**。模型若位于 `wordformat` wheel 内，无论安装哪个 extra，用户都要下载整个 wheel。**"只下自己需要的领域"这一目标无法通过 extras 实现。**

该约束直接决定了下节的形态：必须用独立发行版，而非 extras。

#### 3.5.2 目标形态

| 发行版 | 内容 | 体积量级 |
|---|---|---|
| `wordformat` | 核心（§3.1） | ~2 MB |
| `wordformat-papers` | 论文领域包 + 论文模型 | ~9 MB |
| `wordformat-govdoc` | 公文领域包；**首版仅规则，不绑模型** | 可忽略 |

```bash
pip install wordformat wordformat-papers     # 论文用户
pip install wordformat wordformat-govdoc     # 公文用户
```

用户只为自己的领域付费（体积），核心保持精简。

#### 3.5.3 公文首版只含规则

公文用户不必承担任何模型体积，且该选择有依据：

1. 公文是**强规则域**（GB/T 9704-2012 + 层次序数 `一、`/`（一）`/`1.`/`（1）`），§2.2 已论证规则层在此的权重高于模型层；
2. 规则包体积可忽略，**完全绕开本节的体积问题**；
3. 仅在实测证明规则召回不足时，才为 `govdoc` 引入模型 —— 届时 §7 的实测数据已可支撑该决策，而非现在预先背上一份权重。

#### 3.5.4 落地的必要条件与不采纳的路线

独立发行版要真正可用，须先打通资源锚点：`agent/onnx_infer.py:33-36` 的 `_get_model_dir()` 改为由 DomainPack 提供（即 §3.3 的 `model_path`）。否则外部包中的模型无法加载。

**按需下载不建议纳入本方案。** 该路线已被主动退役（§2.7 记录了原因与守卫逻辑），且公文场景多部署于**内网离线环境**，下载路径本就不可用。若将来确有需求，应作为独立议题重新论证，而非在此顺带引入。

### 3.6 UI 与类别元数据的供给

#### 3.6.1 现状：UI 持有三张领域知识表，且已实测漂移

`WordFormatUI/src/composables/useTagHelpers.js`（94 行）硬编码：

| 表 | 行 | 内容 | 实际来源 |
|---|---|---|---|
| `CATEGORY_CONFIG` | 3-23 | 19 条"类别 → 中文描述" | **抄自 `data/system_prompt.txt`**，非注册表 |
| `LEVEL_MAP` | 25-35 | 类别 → 层级 | 后端 `_level_registry` 的第 4 份副本 |
| `CONF_THRESHOLDS` | 41-65 | 类别 → 阈值 | `base.py:20`（`:39` 注释自述需保持一致） |

消费方：`components/DocTagChecker.vue:107`、`components/NodeDetailPanel.vue:92`、`components/NodeListPanel.vue:50`。

**已出现的分歧（实测，非推演）**：

1. **幽灵类别**：`CATEGORY_CONFIG` 含 `chinese_title` / `english_title`，而后端注册表中**不存在这两个类别**（后端用 `document_title`，见 `structure/settings.py:31`）。二者仅存在于 `data/system_prompt.txt:18-19` —— 这印证了 `CATEGORY_CONFIG` 的抄写来源。
2. **缺失类别**：`CATEGORY_CONFIG` 缺少后端已注册的 9 个类别（`abstract_chinese_content`、`abstract_english_content`、`references_content`、`acknowledgements_content`、`math_block`、`figure_image`、`table_object` 及后处理的 `document_title`、`footer`）。
3. **层级不一致**：UI 的 `LEVEL_MAP` 记 `keywords_chinese` / `keywords_english` 为 **2**（`useTagHelpers.js:28`），而后端注册的是 **3**（`domains/thesis/rules/keywords.py:82,211`）。→ 列表缩进与配色会与后端判定不一致。
4. `caption_figure` / `caption_table` 在 UI 为 level 5，而后端 registry 未为其注册 level（`tree.py` 中取 `999`）。

顺带发现：`data/system_prompt.txt` 在 `src/` 中**无任何消费方**（唯一引用是构建产物 `SOURCES.txt`），属 LLM 版遗留，但它在 package-data 白名单（`pyproject.toml:129-142`）内，**仍随包分发**。

> 结论：UI 侧的领域知识副本不是"将来可能出问题"，而是**已经出问题**。领域包落地时必须一并收敛，否则新增公文类别会让漂移面继续扩大。

#### 3.6.2 改法：类别元数据由后端单一供给

**原则：UI 不再持有任何领域知识，只渲染后端给出的 schema。**

**（1）后端新增 schema 接口**

```
GET /api/domains                  → ["papers", "govdoc"]
GET /api/domains/{name}/schema    → 类别元数据
```

schema 由 DomainPack 提供（§3.3 的 `export_defaults()` 扩展），形态：

```json
{
  "domain": "papers",
  "categories": {
    "heading_level_1": {
      "label": "一级标题",
      "description": "段落以“第X章”或单个阿拉伯数字开头…",
      "level": 1,
      "threshold": 0.6
    }
  },
  "max_level": 3,
  "default_category": "body_text"
}
```

关键是把当前混在一起的两样东西拆开：

- `label` —— 给人看的短名。UI 现在直接把 prompt 措辞（"仅当段落是'摘要'…"）当标签显示，不适合列表场景；
- `description` —— 判定说明，即 `system_prompt.txt` 那段文字，保留用途。

**（2）DomainPack 接口补字段**（对 §3.3 的修订）

```python
labels: dict[str, str]              # 类别 → 显示名
descriptions: dict[str, str]        # 类别 → 判定说明（承接 system_prompt.txt 的角色）
default_category: str = "body_text"
```

**（3）前端改造面比看起来小**

`useTagHelpers.js` 的三个消费函数签名**已经**接受层级映射参数：

```javascript
getNodeIndent(node, levelMap = LEVEL_MAP)              // :77
getLevelColor(node, levelMap = LEVEL_MAP, colors = LEVEL_COLORS)  // :82
```

因此改造主要是：删除三张硬编码表 → 默认值改为由 store 注入的 schema；三个组件改为从 store 取 schema。`LEVEL_COLORS`（6 个色阶，`:37`）是纯呈现层、领域无关，可留在前端。

**（4）三个 API 接口需增加 domain 参数**

当前 `/generate-json`、`/check-format`、`/apply-format` 均无 domain 参数（`api/__init__.py:98,143,197`），仅接收 `docx_file` + `config_file`。需增加 domain 并透传至 `set_tag_main` 与 orchestrate。

**（5）一处易漏的正确性点**

**结果 JSON 必须携带 `domain` 标识，且前端以 JSON 内的 domain 为准渲染**，而非当前选择器的状态。

否则会出现：用户生成 JSON → 切换 domain 选择器 → 前端用新域的 level / threshold 渲染旧域的 JSON → 缩进、配色、低置信高亮全部错位，**且不报错**。这是 §3.2 要消除的静默错配在 UI 层的翻版。

#### 3.6.3 UI 不需要跟着领域包拆分

`src/wordformat/api/static/` 构建产物仅 **272 KB**，且已被 `pyproject.toml:129-142` 纳入 core wheel。

UI 若做到不含领域知识（§3.6.2），即为**领域无关资源**，留在核心发行版是正确的 —— 领域体积问题完全由模型贡献（9.1 MB，§2.7），UI 不参与。这反过来印证了 §3.5.2 的拆分形态：**拆的是模型与其绑定的规则，不是界面。**

#### 3.6.4 顺带清理

`data/system_prompt.txt` 无消费方却在 package-data 白名单内。处理方式二选一：接入为各领域包的 `descriptions` 种子，或从白名单移除。前者更有价值 —— 它本就是一份成文的判定标准。

## 4. 分期路线与改动面估算

### 4.1 缝 A：抽出后处理链（优先，高价值 / 低风险）—— ✅ 已于 2026-09-29 落地

> 实际落点：常量与 13 个函数 → `domains/thesis/postprocess.py`（整链入口 `_thesis_postprocess`，导入即注册）；框架侧只留 `domains/postprocess.py` 注册表（`register_postprocess`/`get_postprocess`，未装配领域返回 None，`parse()` 跳过）。

**做法**：把 `base.py:20-148` 常量与 `base.py:245-628` 的 13 个函数迁至 `wordformat/domains/papers/postprocess.py`；定义 `postprocess(result) -> list[dict]` 协议；`parse()` 改为调用 `self.domain.postprocess(result)`。

**涉及文件**：`base.py`、新增 `domains/`、`classify/tag.py:16`（传入 domain）、`cli.py`。

**风险**：低。函数均为纯函数（输入输出皆为 `list[dict]`），搬迁是机械的。

**测试影响**：`tests/classify/test_tag.py`（702 行）在 `39-51` 行集中 import 了全部 12 个后处理函数，搬迁后仅需改 import 路径，测试逻辑可原样保留。

**收益**：这是解锁公文支持的**必要改动** —— 公文规则替换不再需要触碰核心解析代码。

### 4.2 缝 B：注册表实例化（必要，中风险）—— ✅ 已于 2026-09-29 落地

> 实际落点：`structure/registry.py` 引入 `Registry` 类（每领域独立实例）+ `default_registry`（论文默认，垫片 `_registry`/`_level_registry`/`@register`/`export_defaults` 指向默认实例）+ `get_registry(domain)`；`create_node`、`DocumentTreeBuilder`、`DocumentBuilder.build_from_json`、`TreeBuildingStage` 均接 `registry` 参数；`tree.py:195-224` 硬编码副本已改为注册表派生。

**做法**：`_registry` / `_level_registry` 由模块全局改为 `Registry` 实例属性；`create_node`、`tree_builder` 接收 registry 参数；消除 `settings.py:28-40` 的别名赋值；`settings.py:31-38` 的 `setdefault` 块并入 `papers` 包；**同步消除 `tree.py:195-224` 的硬编码副本**（改为从 registry 派生，使 §2.3 的四副本收敛为一）。

**涉及文件**：`structure/registry.py`、`structure/settings.py`、`structure/node_factory.py`（`:10` import、`:23-24` 查表）、`structure/tree_builder.py`（`:8` import、`:14` 过滤）、`tree.py:195-224`。

**风险**：中。主要来自测试对模块级对象的 patch 依赖，例如：

```python
tests/test_integration.py:318
    with mock.patch("wordformat.structure.node_factory.CATEGORY_TO_CLASS", {}):
```

这类 patch 在实例化后需改为注入 mock registry —— 属于机械改写，但需逐个排查。

**收益**：让 `papers` 与 `govdoc` 共存而不互相覆盖；新增 `heading_level_4` 等公文类别时不再有静默分歧点。

### 4.3 不进领域包的工作（属于核心）

1. **§2.6 的解析层扩展**（页眉 / 页脚 / 文本框 / 表格内段落）—— 领域无关，且是公文场景的真实瓶颈；
2. **公文的 GB/T 9704 preset YAML** —— 注意 `presets/` 目录**当前为空**，规则沉淀目前无处可放，需先确立存放约定。

### 4.4 缝 C：发行版拆分（依赖 §3.5）

**做法**：

1. 核心发行版剥离模型；`papers` 独立发行版携带模型资源；
2. `_get_model_dir()` 改为经 DomainPack 解析锚点（§3.5.4）；
3. `pyproject.toml:129-142` 的 package-data 白名单按发行版拆分；
4. `scripts/build.sh:49-52` 的 PyInstaller `--add-data` 同步调整。

**时机**：与缝 A 同期成本最低 —— 缝 A 本就要把 `parse()` 改为经 domain 调用，锚点解析可一并接入。

**风险**：中。涉及发布流程（`make build` → `scripts/build.sh` / `build.bat`）与两处打包清单的同步，其正确性**无法由单元测试覆盖**（955 个测试均不校验 wheel 内容），需靠发布前的人工验收。

### 4.5 缝 D：UI schema 供给（依赖缝 B）

**做法**：

1. 后端新增 `GET /api/domains` 与 `GET /api/domains/{name}/schema`（§3.6.2）；
2. DomainPack 补 `labels` / `descriptions` / `default_category` 字段；
3. `/generate-json`、`/check-format`、`/apply-format` 增加 domain 参数并透传；
4. 生成结果 JSON 增加 `domain` 字段；
5. 前端删除 `useTagHelpers.js` 的三张硬编码表，改为消费 schema（§3.6.2 第 3 点）。

**时机**：必须在缝 B 之后 —— schema 的来源是 registry 实例，全局注册表未拆干净前无法按域导出。

**风险**：中低。前端改造面小（三个函数签名已支持注入），但涉及 Vue 构建产物更新（`make build-ui`）与三处组件联调。

**收益**：一次性消除 §3.6.1 列出的四类实测漂移（幽灵类别、缺失类别、`keywords` 层级不一致、题注层级无定义），并使新增公文类别不再扩大漂移面。

## 6. 建议决策

1. 采纳**领域包**作为领域知识的组织单元，核心保留领域无关能力（§3.1）；
2. 领域包整体交付"标签集 + 阈值 + 规则 + 权重"四元组（§3.2）；
3. 领域包采用**独立发行版**分发，不使用 extras（§3.5.1、§3.5.2）；
4. **公文首版只含规则、不绑模型**（§3.5.3）；
5. **UI 不持有领域知识**，类别元数据由后端 schema 接口单一供给（§3.6.2）；UI 本身留在核心发行版，不随领域包拆分（§3.6.3）；
6. 先做**缝 A**，再做**缝 B**；发行版拆分（缝 C）与缝 A 同期；UI 改造（缝 D）须在缝 B 之后（§4.5）；
7. 缝 A 落地**之前**先完成 §7 的验证 —— 避免修复一个不存在的问题。

## 7. 未验证的假设（重要）

本文档中关于"论文规则在公文上产生负收益"的判断（§2.2），**全部来自对代码逻辑的静态推演，未经真实公文样本验证**。具体未验证项：

1. 论文模型在公文上把"附件"误判为 `heading_fulu` 的实际频率；
2. `_apply_section_state` 在公文上的实际误触发率；
3. 模型在公文上的整体错分分布（是版式角色判错，还是层级判错）。

**最低验证动作**：取 3–5 份真实公文，运行 `wordf gj` 产出 JSON，人工统计 `category` 与 `comment` 字段的错分分布。

判读方式：

| 观察 | 推论 |
|---|---|
| 错分集中在"该识别为标题的段落被判为 `body_text`" | 解析层 / 规则层问题 → 支持 §2.2、§2.6 的判断，缝 A 应立即执行 |
| 版式角色判对但**层级**判错 | 模型侧问题 → 需重新评估模型替换的优先级 |
| `heading_fulu` 误判率确实高 | §2.2 的负收益结论成立 → 缝 A 应立即执行 |
